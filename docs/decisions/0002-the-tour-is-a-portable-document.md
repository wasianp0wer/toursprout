# 0002 — The tour is a portable document

Status: accepted, 2026-10-13.

## Problem

Sub-project 1 gave the tour a clean, versioned, self-describing schema. It was
still trapped: generated by a Python pipeline into one fixed path, seeded into
a SQLite table at boot, and served by an API that only knew how to read. There
was no way to get a tour out, no way to put one in, and no way to show one to
anybody without running the Python backend. An editor needs somewhere to
write to that isn't a build step, and a tour needs to leave this repository to
be shown to anyone.

## Considered

**Hold the open document as a zip in memory**, assembling and re-flattening it
on every edit. Rejected: the editor needs somewhere to put an uploaded
photograph before the tour is saved anywhere at all, and a zip has no
mid-edit state — every upload would mean rebuilding the whole archive. It also
means every read of `tour.json` decompresses the archive, for no benefit over
a plain file.

**Keep the SQLite table and layer import/export on top of it as a serialization
format.** Rejected: the table only ever existed to make one hard-coded tour
readable at startup. Importing into it and exporting out of it would be strictly
more code than treating the working directory as the document, for a benefit
(indexed queries) nothing here needs — there is one open tour at a time.

## Decision

An open tour is an **unpacked working directory** (`<content_dir>/work/`:
`bundle.json`, `tour.json`, `media/`), not a zip held in memory. Every edit
writes through to it immediately — `Session.write_tour`, `Session.write_config`
— via a sibling-temp-file-plus-`os.replace`, so a crash mid-write lands on the
old file or the new one, never a truncated mix of both.

The working directory **is** the document. The `.zip` bundle
(`backend/app/bundle.py`) is only its portable form: `write_bundle` flattens
the working directory into a zip to leave the machine, and `read_bundle`
validates an incoming zip into a staging directory and only then swaps it in —
through the same `.incoming`/`.outgoing` rename dance `_swap_in` uses — so an
import can replace the open document but can never leave it half-replaced.
Import is the application's only untrusted input, which is why nearly all of
`bundle.py`'s code is about refusing what an archive could lie about: path
traversal, absolute paths, symlinks, backslash and drive-letter names, too
many entries, an archive too large — enforced by counting real decompressed
bytes as they are streamed out, entry by entry, rather than trusting
`ZipInfo.file_size`, which the archive itself controls and `extractall` does
not re-check.

**The departure from the brainstormed design.** "Save" was agreed as writing
back to the bundle the author opened. It is delivered instead as continuous
write-through to the working directory, plus an explicit `GET
/api/session/export` that streams a fresh zip. The reason is not a
preference: a browser cannot write back to an arbitrary file it opened, and
the one API that would let it — File System Access — is not supported broadly
enough to build the editor on. "Open" became an upload (`POST
/api/session/import`) for the same reason: a browser cannot read an arbitrary
server path either, and an upload is the honest equivalent.

The loss is real and is stated plainly here rather than smoothed over: "save
over the file I opened" becomes "export, then go replace the original
yourself." There is no file-level save-in-place at all; there is a document
that is always saved (to the working directory) and a zip you can ask for at
any point. The gain — no server-side path handling, nothing to lose on a
crash, nothing to configure about where things live — is real too, but **this
trade was not put to the author as a choice; it was discovered to be the only
one available and taken.** It is flagged here for the author to overrule: if
the File System Access API's support footprint changes, or if the workflow
cost of "export and replace by hand" proves worse in practice than it looks
on paper, this is the decision to revisit, not a detail inside it.

**One set of `tour-data/` URLs.** The viewer fetches `tour-data/config.json`,
`tour-data/tour.json` and `tour-data/media/<mediaId>`, relative to the page,
in both the editor and a published site. In the editor FastAPI mounts
`StaticFiles` over the working directory at `/tour-data` (`_mount_tour_data`
in `main.py`); in a published site (`publish.py`) those are ordinary files
sitting next to `index.html`. A build flag or a runtime deployment check was
not considered seriously: either would mean two code paths through `TourApi`
that must be kept in agreement by hand, forever, for a distinction the viewer
has no actual need to know about. One set of URLs makes "the viewer works
identically whether a backend is running or not" true by construction rather
than true because nobody has yet found the place the two paths disagree.

The prefix is `tour-data/`, not the more obvious `media/`, because Angular's
own production build already emits a `media/` directory — Leaflet ships its
marker icons there. Publishing tour media to `media/` at the site root would
silently overwrite, or be overwritten by, Angular's own assets; confirmed on a
real build output before this was taken as settled rather than assumed.

**The database and four endpoints were deleted, not deprecated.**
`GET /api/config`, `GET /api/tours`, `GET /api/tours/{id}` and
`GET /api/media/{id}`, the SQLite `tours` table, and the startup seeding that
populated it are all gone, along with `db.py`. They existed to serve a
read-only prototype that generated exactly one tour at build time; a document
model that writes through to a working directory has no read path left for
them to serve, and a seeding step that nothing reads any more is a trap for
the next person who wonders why editing content requires restarting the
server. `media.py`'s hand-rolled HTTP Range parsing was replaced, not simply
lost: Starlette's `StaticFiles` already serves Range requests correctly
through the `/tour-data` mount (206, `Content-Range`, 416, suffix ranges), so
the custom parser — which existed only because media used to be addressed by
opaque id through its own route rather than by path — had nothing left to do.

That replacement had one caveat that was not free: Python's stdlib
`mimetypes` table disagrees with every browser about `.m4a`, answering
`audio/mp4a-latm` — an RTP/SDP payload name — rather than `audio/mp4`, and
about `.wav`, answering `audio/x-wav` rather than `audio/wav`. `media.py`'s own
table had pinned the browser-correct answers for the prototype's entire life;
losing that table without comment would have silently broken narration
playback, since the `<audio [src]>` in `stop-panel.ts` has no `type` attribute
to fall back on. `main.py` now calls `mimetypes.add_type` for both extensions
at import time, specifically to restore what the deleted table was quietly
doing. This is the one piece of `media.py` that could not simply be deleted in
favor of the framework doing the job — the framework's answer for these two
extensions is wrong, not merely different.

**The Mapillary token travels with a published site.** `config.json` is
generated at publish time from the backend's settings and copied into the
site's `tour-data/`, token included, because mapillary-js runs entirely in the
browser and has no other way to authenticate. This looks like shipping a
secret and is not one: it is a public client token, meant to be presented by
browser code, and a published site cannot avoid including it any more than it
could avoid including its own JavaScript.

## Costs

A new user-facing workflow — upload, continuous write-through, export, publish
— replaces the simpler mental model of "open a file, edit it, save it," for an
author who was told the simpler model was agreed on. The cost is not
hypothetical: it is the entire "departure from the brainstormed design"
section above, and it is the first thing a returning author should be told
about this sub-project, not a footnote they discover by using the editor.

`backend/tours.db` is still on disk — 28 KB, gitignored, untracked, last
written before this sub-project started. Nothing reads or writes it any more;
it is a stale artifact of the deleted database and safe to delete by hand.

The deleted `test_media_type_detection` parametrization also covered `.mp3`,
extension case-insensitivity (`.JPG`), and the unknown-extension fallback to
`application/octet-stream`. None of those three is retested after the
deletion of `media.py`, because the stdlib `mimetypes` table already agrees
with the old hand-rolled one on all three — confirmed by hand, not assumed.
Only the two cases where stdlib disagrees (`.m4a`, `.wav`) are pinned, by the
`add_type` calls in `main.py` and tests that exercise the real `/tour-data`
mount rather than calling `mimetypes` directly.

## How the deferred features land on this

- **The editor (sub-project 3)** is the reason any of this exists: it needs
  `GET /api/session` and `PUT /api/session/tour` to have somewhere to write,
  and everything else here — import, export, publish — is what makes that
  somewhere a document an author can actually get in and out of this
  application. `SessionApi` on the frontend is deliberately the only piece
  that talks to `/api`; `TourApi` must keep working with no backend running at
  all, because a published site has none.
- **Multi-tour authoring**, if it ever arrives, is bounded by today's "one
  open document" assumption throughout `Session` and the mount at
  `/tour-data`. Nothing here rules it out, but nothing here was built to
  support it either; it would mean a working directory per tour and a prefix
  or session id in the URL, which is exactly the kind of "second code path"
  the single-`tour-data/`-prefix decision above was trying to avoid needing.
- **If File System Access support broadens** enough to build on, the departure
  recorded above is the thing to revisit first, not work around: a real
  save-in-place becomes possible again, and the question is whether it is
  worth adding alongside continuous write-through and export, or instead of
  it.
