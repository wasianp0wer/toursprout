# Bundle and publish: the tour as a portable document

Sub-project 2 of 4. See
`docs/superpowers/specs/2026-10-12-authoring-application-overview.md` for how
the four fit together, and
`docs/superpowers/specs/2026-10-12-schema-v2-design.md` for the document this
one moves around.

## Why

Sub-project 1 made the tour document a clean, versioned, self-describing thing.
It is still trapped: generated by a Python pipeline into one fixed path, seeded
into SQLite at boot, and served by an API that only knows how to read. There is
no way to get a tour out, no way to put one in, and no way to show one to
anybody without running Python.

This sub-project makes the tour a **portable document** and gives it two exits:
a `.zip` bundle that round-trips, and a static site that needs no backend. The
editor in sub-project 3 then has somewhere to save, which is the precondition
for building it at all.

## What a bundle is

A `.zip` whose contents are exactly what a published site serves:

```
fairfax-old-town.zip
  bundle.json          { "bundleVersion": 1, "tourId": "...", "created": "..." }
  tour.json            the schema v2 document
  media/               every file the document references, by mediaId
    court-1863.jpg
    narration-historic-courthouse.m4a
    pano/pano-historic-courthouse.jpg
```

`bundle.json` is deliberately separate from `tour.json`. It describes the
*container* — which can gain compression choices, checksums or multi-tour
support later — while `tour.json` stays purely the schema's business.
`bundleVersion` is independent of `schemaVersion`: a v1 bundle can carry a v2
document, and a reader checks both.

A `mediaId` in the document is a bare filename, so `media/<mediaId>` resolves
with no registry and no indirection. That is already true in v2 and is the
property that makes this format trivial.

## The working directory, and what "save" means

The editor needs somewhere to put an uploaded photograph before the tour is
saved anywhere. So an open tour is an **unpacked working directory**, not a zip
held in memory:

```
<content_dir>/work/
  bundle.json
  tour.json
  media/
```

Every edit writes through to `work/tour.json` immediately. The working
directory **is** the open document; the zip is its portable form.

**This changes what the agreed "Save / Save as" means, and it is the one place
this spec departs from the brainstormed design.** A browser cannot write back
to a file it opened — the File System Access API exists but is not supported
broadly enough to build on. So:

| Agreed | Delivered | Why |
| --- | --- | --- |
| Open a bundle | Upload a `.zip` (multipart POST) | A browser cannot read an arbitrary path; an upload is the honest equivalent and needs no path handling on the server |
| Save | Continuous — every edit writes to the working directory | Nothing to lose on a crash; closer to "the filesystem is the library" than an explicit save would be |
| Save as | Export: download a `.zip` | The portable artifact, produced on demand |
| Publish | Download a static-site `.zip` | Unzip it on any host |

The practical loss is that "save back over the file I opened" becomes "export
and replace it yourself". The practical gain is no server-side filesystem
paths at all, which removes a path-traversal surface and a whole class of
"which directory am I in" confusion from a tool meant to be run casually.

This is flagged for the author to overrule.

## One data path, two deployments

The most important decision here. The viewer must work identically whether a
backend is running or not, and the cheapest way to guarantee that is to give
it **one** set of URLs that both deployments satisfy:

```
tour-data/config.json      { mapillaryToken, tileUrl, attribution }
tour-data/tour.json        the schema v2 document
tour-data/media/<mediaId>  the media files
```

All relative to the page. In the editor, FastAPI serves `tour-data/` from the
working directory. In a published site, those are ordinary files sitting next
to `index.html`. **No runtime detection, no build flag, no second code path.**

The prefix is `tour-data/`, not `media/`, because Angular's build already emits
a `media/` directory for Leaflet's bundled marker images. Publishing tour media
to `media/` would collide with them.

Range requests keep working: Starlette's `StaticFiles` serves them, and so does
every static host, which is what the narration audio needs.

### What this replaces

`GET /api/config`, `GET /api/tours`, `GET /api/tours/{id}` and
`GET /api/media/{id}` all go away, and with them `backend/app/db.py`,
`backend/app/media.py` and the `tours` SQLite table. The database existed to
serve a read-only prototype; a document model has no use for it, and keeping a
seeding path that nothing reads would be a trap for the next reader.

`backend/app/media.py`'s hand-rolled range handling is deleted rather than
ported: `StaticFiles` does the same job, and the custom code only existed
because media was addressed by id rather than by path. Its tests go with it.
**This is the one place in this plan where tests are deliberately removed**,
and the justification is that the behaviour they covered is now provided by the
framework — not that it stopped mattering.

## The session API

Small, and all of it about the container rather than the content.

| Endpoint | Does |
| --- | --- |
| `GET /api/session` | `{ tourId, title, dirty, mediaCount }` for the open document, or `{ open: false }` |
| `POST /api/session/new` | Start an empty working directory with a one-stop skeleton tour |
| `POST /api/session/import` | Multipart `.zip` upload; validate, then replace the working directory |
| `PUT /api/session/tour` | Replace `tour.json` wholesale, validating first; rejects on `ValidationError` with the message |
| `GET /api/session/export` | Stream the working directory as a `.zip` download |
| `GET /api/session/publish` | Stream a static site as a `.zip` download |

`PUT` takes the whole document rather than patching parts of it. The document
is tens of kilobytes, the editor holds it all in memory anyway, and whole-document
writes make "the file on disk always validates" trivially true. Granular
endpoints can come later if profiling ever asks for them; they are not needed
now and would multiply the validation surface.

Media upload (`POST /api/session/media`) belongs to sub-project 3, with the
recording UI that produces the files. This sub-project only has to serve media
that a bundle already contains.

## Import is a trust boundary

A `.zip` from outside is the only untrusted input this application has, and it
arrives as an archive, which is the classic way to write files where you did
not intend to. Import must:

- **Reject path traversal.** Any entry whose normalised path escapes the
  extraction root, is absolute, or is a symlink, aborts the whole import.
  Python's `ZipFile.extractall` does not protect against this adequately on its
  own; entries are checked individually before anything is written.
- **Refuse an oversized archive** — a cap on both the entry count and the total
  uncompressed size, so a zip bomb fails fast rather than filling the disk.
- **Validate before replacing.** Extract to a temporary directory, parse and
  migrate `tour.json`, validate it as v2, confirm every `mediaId` the document
  references exists in `media/`, and only then swap it in. A failed import must
  leave the previously open document exactly as it was.
- **Accept a v1 bundle**, by running `migrate_v1_to_v2`. That is the whole
  reason the migration stays in the tree.

The reverse check matters too but is a warning, not an error: media files
present in the bundle that no overlay references are reported, not deleted. An
author mid-edit will often have orphans, and silently discarding their uploads
would be the worse failure.

## Publish

`GET /api/session/publish` streams a zip containing the built Angular bundle
plus `tour-data/`. Unzipped anywhere a static host can see, it is the tour.

The build output must exist; if `frontend/dist/...` is missing, publish fails
with a message saying to run `make build` rather than producing a broken site.

`config.json` is generated at publish time from the backend's settings, so the
Mapillary token travels with the site. That token is a public client token —
mapillary-js runs in the browser and cannot use anything else — so this is not
a leak, but it is worth stating plainly because it looks like one.

## Frontend changes

- `TourApi` loses `getConfig`/`listTours`/`getTour`/`mediaUrl` against `/api`
  and gains the three `tour-data/` fetches. The interface it presents to
  `TourStore` and the components barely changes, so this is mostly one file.
- A `SessionApi` service for the session endpoints, used by sub-project 3's UI.
  This sub-project needs only `GET /api/session` and `PUT /api/session/tour`.
- `index.html` needs `<base href="./">` so a published site works from a
  subdirectory, which is where most static hosts put things.

## Out of scope

The editor UI, media upload, audio recording, the re-homed content scripts, AR,
themes, Omeka. Multi-tour bundles. Compression tuning. Checksums.

`content/source/stops.json` and the `make content` pipeline stay exactly as
they are; they retire in sub-project 3.

## Testing

TDD throughout. The 162 backend and 210 frontend tests stay green except where
they test the deleted endpoints, which are removed with them.

**Backend.** Round-trip is the headline property: the shipped tour, exported
and re-imported, produces a byte-identical `tour.json` and the same media set.
Beyond that: import rejects a traversal entry (`../../etc/passwd`), an absolute
path, a symlink, an over-large archive and an over-many-entry archive; import
of a v1 bundle migrates it; import of a bundle whose document references a
missing media file fails; a failed import leaves the open document untouched;
orphaned media produce a warning and not an error; `PUT` rejects an invalid
document with a useful message and leaves the previous one on disk; publish
without a build fails with a clear message; publish output contains
`index.html`, `tour-data/tour.json` and every referenced media file.

**Frontend.** The viewer loads entirely from `tour-data/` with no `/api` call —
asserted by a fetch spy, since the whole static-deployment claim rests on it.
`real-tour.spec.ts` keeps loading the real document and keeps its role as the
regression guard.

**Acceptance.** `make check` green, and a published directory served by any
static file server renders the tour. That last part **cannot be verified
here** — no browser runs in this sandbox — so the jsdom assertion that nothing
touches `/api` is the strongest available proxy, and the author should spot-check
a published site outside the sandbox before trusting it.

## Risks

- **Deleting the database and four endpoints is the largest subtraction this
  project has had.** It is right — nothing will read them — but it is
  irreversible in the sense that the next sub-project builds on their absence.
  The mitigation is that it happens behind a green suite, in its own task, with
  the removed behaviour either reprovided by `StaticFiles` or genuinely dead.
- **Zip handling is a security boundary** and is being written from scratch.
  The traversal, symlink and size tests are not optional coverage.
- **`<base href="./">` changes how every asset URL resolves** and can break the
  dev server subtly. It is tested by building, and needs the author's eyes once
  outside the sandbox.
